# Code Review Reply — 回复处理与文档更新

## 触发条件
- 用户针对已有的 code review 结果提供开发者回复
- 用户说"开发者回复了"、"review reply"、"回复 P0 问题"等

## 输入
- 开发者的回复内容（文本、截图、或口述）
- 对应的 review 文档路径（`repo-references/[仓库]/[分支]-review-[timestamp].md`）

## 执行步骤

### Step 1: 定位 review 文档
```bash
# 找到最新的 review 文档
ls -t repo-references/[仓库名]/*-review-*.md | head -1
```
如果用户指定了具体文档则直接使用。

### Step 2: 读取现有 review 内容
读取完整 review 文档，理解每个问题的:
- 问题编号和严重级别
- 问题描述和文件位置
- 原始风险评估

### Step 3: 逐条评估开发者回复
对每个回复进行独立评估:

| 回复类型 | 评估方式 | 处理 |
|---------|---------|------|
| "不会发生" / "已确认安全" | 验证开发者理由是否成立 | 降级或保持 |
| "已知风险，可接受" | 确认业务决策合理 | 降级为已知风险 |
| "已修复" / "已处理" | 确认修复方案是否充分 | 标记已修复 |
| "不同意" | 重新分析，给出更详细论据 | 保持或调整 |
| "后续处理" | 确认计划合理性 | 标记为 deferred |

**评估原则**:
1. **尊重开发者判断**: 开发者最了解业务上下文和生产环境
2. **独立验证**: 不盲目接受，需要用代码/逻辑验证回复的合理性
3. **给出明确结论**: 每个问题必须有 ✅降级 / ⚠️部分降级 / ❌保持 的明确判定
4. **遗留建议**: 即使降级，也给出低成本的防御性改进建议

### Step 4: 更新 review 文档
在文档末尾追加新的 section:

```markdown
---

## [N]、开发者回复与结论修订（第 M 轮）

> **回复时间**: [timestamp]
> **回复人**: [name]
> **回复内容摘要**: [summary]

---

### [N].1 [问题编号]: [问题标题]

**开发者回复**: "[原文引用]"

**Review 结论**: ✅/⚠️/❌ **[修订后级别]**

[评估分析和理由]

[遗留建议（如有）]

---

### [N].[last-2] 修订后问题优先级汇总

| 原级别 | 问题 | 修订后级别 | 原因 |
|--------|------|-----------|------|
| ... | ... | ... | ... |

---

### [N].[last-1] 修订后问题总览

| 严重级别 | 修订前数量 | 修订后数量 | 说明 |
|---------|-----------|-----------|------|
| 🔴 P0 | X | Y | ... |
| 🟠 P1 | X | Y | ... |
| 🟡 P2 | X | Y | ... |
| 🟢 P3 | X | Y | ... |

**结论**: [是否可合并/需要修复哪些项]

---

### [N].[last] 剩余建议（合并前处理）

| # | 问题 | 建议 | 预估工时 |
|---|------|------|---------|
| ... | ... | ... | ... |

---

*Reply reviewed by [model] via Hermes Agent — [timestamp]*
```

### Step 5: 向用户汇报
用简洁的表格总结:
1. 每个问题的修订结果（降级/保持/已修复）
2. 修订后的 P0/P1/P2/P3 数量
3. 最终结论（是否可合并）
4. 剩余建议清单

## 多轮回复支持
- 如果已有 `## 九、开发者回复与结论修订`，新一轮追加为 `## 十、开发者回复与结论修订（第 2 轮）`
- 每轮修订基于上一轮的修订后级别，不重置
- 在最新一轮的"修订后问题总览"中显示累计变化

## 输出文件
- 更新现有 review 文档（追加 section，不覆盖原有内容）
- 文件路径不变: `repo-references/[仓库]/[分支]-review-[原始timestamp].md`

## Pitfalls
1. **不要覆盖原有内容**: 只追加新的 section，用 `patch` 的 `replace` 模式替换末尾签名行
2. **独立评估**: 即使开发者说"没问题"，也要从代码层面验证其理由是否成立
3. **不要过度降级**: 如果开发者理由不充分，应保持原级别并给出更详细的论据
4. **时间戳**: 使用当前时间作为回复时间，保留原始 review 时间不变
5. **回复可能是部分回复**: 开发者可能只回复了部分问题，未回复的问题保持原级别
6. **回复可能引入新问题**: 开发者的修复方案可能引入新风险，需要在评估中指出
